# Game effect files: parsing and inventory (lane FX)

The plan's P3 starts from the effect text UNI2, MBTL and DFCI ship in `Shader/*.txt`.
`src/rhi/d3d9/fx/fx_parse.{h,cpp}` reads it. This note records the dialect as it actually
appears in the three installs and what the parser does with each construct.

## Encoding

All files are CP932 (Shift-JIS) with CRLF, and comment lines carry Japanese. Some files
also contain a bare `0x85`, which `file(1)` reports as a "NEL" line terminator; CP932 maps
`0x85` to U+0085, and the parser treats it as an ordinary byte. Trail bytes can be `0x5C`
(`\`), so the text is **decoded before anything else** (`fx::Cp932ToUtf8`, a generated
table from Python's `cp932` codec, `tools/fx/gen_cp932.py`). Scan only UTF-8 afterwards: a
continuation byte is never `0x2F` or `0x2A`, so comment stripping cannot eat Japanese text.

## What appears, and how it is parsed

| Construct | Appears as | Parsed into |
|---|---|---|
| Preprocessor | `#define CHARARECTCHECK (0)`, `#define POSBOADER (0.35f)` | `Item::Preproc`, kept as text and emitted verbatim |
| Struct | `struct VS_OUTPUT { ... };` | `Item::Struct`, kept as text |
| Prototype | `float GetAngPosUV( float2 uv );` | `Item::Raw`, kept as text (never defines a uniform) |
| Function | `float4 PS_X( VS_OUTPUT In ) : COLOR0 { ... }` | `Function` (name + head/body text), emitted verbatim |
| Texture | `texture tex_Fade = NULL;` / `texture g_diffuseMap;` | `Texture`; dropped by `MakePassHlsl` (the sampler carries it) |
| Sampler | `sampler2D Tex = sampler_state { texture = <tex_Fade>; MagFilter = Linear; };` | `Sampler` with `values` in file order and the bound `texture` |
| Sampler (DFCI) | `sampler DiffuseTextureSampler = sampler_state { Texture = <diffuse_texture>; };` | same, keyword `sampler`, capital `Texture` accepted |
| Uniform | `float g_Power;`, `float g_fTable[5] = {...};`, `float4 g_mWorld < string UIName = "World"; >;` | `Uniform` with `arraySize`, `defaultValue`, `annotations` |
| Semantic uniform | a declaration whose initialiser carries `:` before `;` | `semantic` captured; a function return semantic stays in the function head |
| Technique | `technique TecNormal { pass P0 { ... } }` | `Technique` with passes |
| Pass shaders | `VertexShader = compile vs_3_0 VS_CharaDrawV();` (`pixelShader`/`vertexShader` too) | `Pass::vs` / `Pass::ps`: profile, entry, args |
| Pass state | `AlphaBlendEnable = True; ZEnable = False;` | `Pass::states` in file order |

A commented-out shader clause (`// PixelShader = compile ...`) is stripped with the comment,
so a pass with a commented VS compile yields `vs.present == false` and only a PS, which is
exactly what the games rely on for their full-screen passes.

## `MakePassHlsl`

For one pass it emits plain HLSL: every declaration in file order, `texture` objects dropped,
each sampler as `sampler2D NAME : register(sN)` numbered in **declaration order** (0-based, the
way D3DX assigns sampler registers), techniques gone. `D3DCompile` compiles `pass.vs.entry`
(`vs_3_0`) and `pass.ps.entry` (`ps_3_0`/`ps_2_0`) from that single source. The sampler's
`texture = <tex>` binding is metadata the runtime resolves to a device texture; the emitters
never renumber samplers, so a pass's `s0`, `s1`, ... match the order the game's file declared.

## Rules kept

- Pure C++: no D3D, no `windows.h`. Builds and is tested on both platforms.
- The generated table is checked in so no build step needs Python at compile time.
- Never emit or commit the games' HLSL text: the inventory and this doc carry names only.

## Compiling every pass (deliverable 3)

`tools/fx/fxcompile.cpp` (Windows, ctest `fx_compile`, label `gpu`) loads
`d3dcompiler_47.dll` with `LoadLibrary`, compiles each pass's VS and PS from
`MakePassHlsl` with `D3DCOMPILE_OPTIMIZATION_LEVEL1`, and reads the constant table
out of the returned bytecode with `fx::ParseConstantTable`
(`src/rhi/d3d9/fx/fx_ctab.cpp`, the documented `D3DXSHADER_CONSTANTTABLE`).

- The `CTAB` payload is the fourcc followed by the struct; the struct's offsets
  are relative to the struct, not the fourcc.
- A `D3DSIO_COMMENT` token carries its length in DWORDs in bits 16-30; there is no
  separate length DWORD. `fx_ctab` pins this layout on a blob built in the test,
  so `fx_compile` can trust it.

Result (regenerated by ctest `fx_compile`, written to
`tools/render_parity/fx_compile.tsv`, names and registers only): **216 shaders, 0
FAIL**, across the same three installs. That is the gate: a failure here would
mean the emission, not the game's file, since D3DX loads all of them.
